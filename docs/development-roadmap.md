## 2. 状态定义

| 状态 | 含义 |
|---|---|
| 规划中 | 已定义范围、依赖和验收标准，尚未开始编码 |
| 开发中 | 正在实现，允许存在未完成代码 |
| 待验收 | 代码和自测已完成，等待用户查看和确认 |
| 已完成 | 用户确认通过，并已记录验证结果 |
| 暂缓 | 有明确原因暂不推进，不代表功能失败 |

## 4. 第一阶段前端约束

后续前端开发必须遵守以下现有风格：

| 维度 | 约束 |
|---|---|
| 页面结构 | 延续顶部导航、中央对话区、右侧产物区的工作台布局 |
| 色彩 | 延续暖灰背景、半透明白色面板、黑色主操作、蓝色强调色 |
| 组件 | 优先复用现有 `btn`、`card`、`input`、Tailwind surface/primary 色阶和 Lucide 图标 |
| 圆角与层次 | 延续 `rounded-2xl/3xl`、柔和阴影和轻边框，不引入突兀的高对比视觉 |
| 文案 | 使用简洁中文，状态、错误和按钮文案必须明确说明下一步 |
| 状态 | 每个异步操作必须有加载、成功、失败、取消、重试和空状态 |
| 响应式 | 桌面端保持现有工作台比例，移动端使用抽屉或底部操作区 |
| 可访问性 | 关键操作支持键盘、焦点可见、图标按钮提供 aria-label，不仅依赖颜色传达状态 |
| 数据边界 | 后端事实状态、Zustand 页面状态、组件临时状态分开维护 |
| 兼容性 | 新 SSE 字段采用向后兼容的可选字段，不改变已有聊天和产物事件语义 |

## 5. 第一批交付内容：P0-01

本批只包含工程管理和设计约束，不改变业务代码：

1. 将统一开发规范复制到仓库 `docs/`，纳入 Git 管理。
2. 建立本路线跟踪表，明确每个功能的前端、后端、难度和验收点。
3. 明确当前前端风格、响应式、状态管理和兼容性规则。
4. 在用户确认前，P0-01 保持“待验收”，不标记为“已完成”。

## 6. 后续验收流程

每个功能按以下顺序推进：

1. 明确本批范围、非目标和验收标准。
2. 在功能分支中实现，不直接修改 `main`。
3. 执行与风险匹配的构建、类型检查、测试和手工回归。
4. 将状态改为“待验收”，向用户展示变更文件、功能路径和验证结果。
5. 用户确认后，再将状态改为“已完成”，记录提交或验证信息。
6. 继续下一批功能。
