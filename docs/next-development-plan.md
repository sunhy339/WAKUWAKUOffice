# WaKuOffice 后续开发方案

> 版本：v1.0
> 日期：2026-10-21
> 依据：`docs/universal-software-development-standard.md`、`docs/development-roadmap.md`
> 原则：先收尾当前已实现能力，再按依赖拆分新功能；每批从 `develop` 创建独立分支，完成自测和服务器验证后交给用户验收，未获确认不合并。

## 1. 当前判断

项目已经具备 Rust Axum 服务端、React 工作台、SQLite/MySQL 数据访问、JWT 认证、SSE 对话、Agent 工具注册表、模型能力配置和 MinIO/S3 适配层。当前主要问题不是缺少基础框架，而是部分能力还没有完成最终验收，部分新需求需要在现有边界上继续拆分，避免把支付、模型路由、历史恢复同时改成一个大功能。

当前优先级按以下顺序确定：

1. 先关闭会话、历史、产物链路的已知风险；
2. 再补齐历史过程的可复查体验；
3. 稳定模型能力路由和设置页；
4. 最后做版本管理、多文件上下文和商业化能力。

## 3. 第一批新开发：历史执行过程恢复

### 3.1 目标

历史会话重新打开后，用户可以看到可复查的执行阶段、工具调用、工具结果、产物生成和错误状态；不展示模型隐藏思维链，不改变已保存的聊天消息和产物事实。

### 3.2 现状与根因

- 服务端已经有 `session_process_events`/`process_events` 持久化能力，并会记录阶段、工具、产物和错误摘要。
- 前端当前更偏向把过程当作当前任务的临时状态，历史恢复时只展示很少的恢复提示，导致用户看到“恢复了会话”但看不到之前发生了什么。
- 历史产物采用异步加载，过程恢复不能重新依赖大体积产物 payload，否则会再次出现恢复慢或空白。

### 3.3 实现边界

| 层 | 方案 |
|---|---|
| 数据 | 继续复用 `SessionProcessEvent`；只补充稳定的 `kind/title/detail/status/tool/at` 字段，不保存原始隐藏推理链 |
| 接口 | 历史详情返回消息和轻量过程事件；保持旧接口字段兼容，旧会话缺少过程时展示兼容空状态 |
| 前端 | 历史过程使用与当前过程面板同一视觉组件；按时间顺序展示，支持折叠工具详情和错误详情 |
| 状态 | `restoring`、`ready`、`partial`、`failed` 与当前 SSE 状态分开，避免恢复历史覆盖正在运行的任务 |
| 性能 | 过程详情只保留必要摘要，长工具结果截断；产物继续独立异步加载 |
| 验收 | A→B→A、刷新 URL、旧会话、含图片/流程图/PPT 的大产物会话分别验证 |

难度：中；预计 1～2 天。主要风险是历史数据格式兼容和过程事件与消息顺序不一致，不需要新增中间件。

## 4. 第二批：模型能力路由收尾

模型能力配置已经有数据结构和基础选择逻辑，下一步不是重写，而是完成“实际执行路径都使用同一套路由”的收口。

### 4.1 范围

- 普通对话/工具调用：使用 `text + tool_calling`；
- 图片识别：使用 `vision`；
- 文生图：文本规划使用文本模型，图片执行使用 `image_generation`；
- 图生图：执行模型必须具备 `image_edit`，并校验参考图存在；
- 视频：方案使用文本模型，生成使用 `video_generation`；
- 无匹配模型时，在执行前返回可读错误，不生成假产物；
- 保留旧环境变量和旧 `models` 列表作为兼容回退。

### 4.2 开发顺序

1. 为图片和视频工具补齐统一 `ModelRequirement` 输入；
2. 将现有环境变量回退封装成 Provider Adapter；
3. 增加能力测试接口和失败原因脱敏记录；（已实现）
4. 设置页补充“当前路由预览”和“按能力测试”状态；（已实现，媒体测试需用户主动点击）
5. 使用真实网关验证 `Responses`、图片接口和至少一种视觉输入。

难度：中高；预计 5～8 个工作日。当前最大不确定性是不同 OpenAI 兼容网关对图片、视频和 Responses 的协议差异，因此先稳定能力契约，再扩展供应商适配。

## 5. 第三批：产物版本管理

### 5.1 目标

PPT 单页修改、文档重生成和图片迭代后，用户可以查看历史版本，并在确认后恢复某个版本。

### 5.2 建议设计

- 新增不可变的 `artifact_versions` 表，保存 `artifact_id`、`session_id`、`version`、`payload`、`created_by`、`created_at`；
- 当前 `session_artifacts` 继续作为快速读取的当前快照，版本表作为历史事实；
- 写入当前产物时在同一事务中追加版本快照，版本号由服务端生成，不能由前端指定；
- 恢复不是物理删除版本，而是创建一个新的当前版本，保证可回滚；
- 接口层增加列表、查看、恢复三个端点，全部检查用户归属；
- 前端沿用产物面板风格，先做版本列表和恢复确认，不增加独立编辑器。

难度：中；预计 3～5 个工作日。依赖：PPT/文档/图片产物的统一 ID 和当前版本语义先稳定。

## 6. 第四批：多文件上下文与来源展示

### 6.1 目标

用户可以在一个对话中选择多个文件作为输入，生成结果时能看到引用了哪些文件、哪些文件影响了结果。

### 6.2 设计

- 增加 `session_sources` 关系记录，保存会话、文件、引用类型和权限快照；
- 对话请求只传文件 ID 和必要的展示信息，服务端再次检查所有权并提取正文；
- 工具输入上下文带来源标识，但不把整份大文件重复写入每条消息；
- 产物增加 `source_refs` 元数据，前端显示来源标签和可定位入口；
- 文件删除后历史会话仍保留来源名称和“文件已不可用”状态，不泄露新文件内容。

难度：中高；预计 4～7 个工作日。依赖：文件权限、对象存储和历史恢复收尾完成。

## 7. 第五批：账户、积分与 VIP/付费

这部分属于在线应用商业化能力，不建议在本地单人模式中强行启用。现有用户表、JWT 和在线模式可以作为基础，但不能直接在用户表增加一个可变 `balance` 字段代替账本。

### 7.1 推荐分期

| 阶段 | 内容 | 难度 | 预计工作量 |
|---|---|---:|---:|
| B1 | 积分账户、消费规则、冻结/扣减/退款账本 | 中高 | 3～5 天 |
| B2 | 套餐、VIP 权益、额度和模型/工具权限 | 中 | 2～4 天 |
| B3 | 订单、支付回调、幂等和对账 | 高 | 5～10 天 |
| B4 | 管理页面、用户账单、消费明细和运营调整 | 中 | 3～5 天 |

### 7.2 数据和架构

- `credit_accounts`：用户当前可用额度的投影；
- `credit_ledger`：每一笔充值、消费、退款、赠送和调整的不可变流水；
- `plans`/`subscriptions`：VIP 套餐和有效期；
- `orders`/`payment_events`：订单状态和第三方回调幂等记录；
- 所有消费在数据库事务中校验权益、冻结额度、执行任务和确认扣减，不能只依赖前端显示；
- 先做 `PaymentPort`/Provider Adapter，再接具体支付渠道；没有确定支付渠道和经营规则前，不写死支付实现；
- Redis 只用于限流、短期幂等锁和缓存，不能作为积分账本或订单事实来源；
- 本地模式默认不显示充值入口，可使用开发额度或关闭计费策略。

### 7.3 前端规划

沿用当前设置弹窗、顶部用户入口和暖灰卡片风格，逐步增加：账户概览、VIP 状态、积分余额、消费明细、套餐页、支付结果页。每个异步操作都必须具备加载、成功、失败、取消和重试状态；支付结果以服务端回调为准，不能以浏览器跳转成功作为最终依据。

## 8. 推荐开发顺序与分支

| 顺序 | 分支 | 主要内容 | 是否现在开发 |
|---:|---|---|---|
| 0 | `feature/artifact-finalization-guard` | 产物失败收口、远程 smoke、文档收尾 | 当前 |
| 1 | `feature/history-process-restore` | 历史过程恢复和兼容旧会话 | 当前分支验收后开始 |
| 2 | `feature/model-route-finalization` | 图片/视频/视觉统一能力路由和测试 | 当前进行中 |
| 3 | `feature/artifact-versioning` | 产物版本列表、恢复和事务 | 第 2 批稳定后 |
| 4 | `feature/multi-file-context` | 多文件上下文、来源引用 | 对象存储和权限稳定后 |
| 5 | `feature/credits-entitlements` | 积分账本和 VIP 权益，不含具体支付渠道 | 在线产品规则确定后 |
| 6 | `feature/payment-provider` | 订单、支付适配器、回调和对账 | 积分权益验收后 |

每个分支均遵循：需求/完成定义 → 设计 → 实现 → 本地门禁 → 服务器 smoke → 用户验收 → 合并 `develop`。未验收分支之间不互相覆盖；需要共用代码时只挑选已验证的独立提交。

## 10. 当前批次进展：视频候选模型回退

本批次已先完成视频生成链路的服务端收口：

- 文生视频和批量分镜都从 `video_generation` 能力路由取得有序候选模型；
- 创建任务失败时才尝试下一个候选模型，并把失败原因压缩到过程状态和最终错误中；
- 某个模型成功创建任务后，后续轮询、下载和产物记录固定使用同一条路由，避免重复创建或错用任务 ID；
- 批量分镜按镜头独立回退，单镜头失败不影响其他镜头，并在产物元数据中记录实际使用模型；
- 图片、普通对话和历史会话路径未改动。

本地 `cargo check` 和 39 项 Rust 测试已通过。设置页已补充“当前能力路由”预览卡片，沿用现有暖灰卡片、黑色主按钮和 Lucide 图标风格，展示普通对话、识图、文生图、图生图和视频生成的首选/备用模型。服务器页面已部署验证；本项需要用户验收后才合并到 `develop`。下一步再补按能力主动测试，并把测试结果回写到模型状态。

当前分支 `feature/model-capability-checks` 已补充按能力主动测试：文本、工具调用和视觉使用最小对话请求；文生图、图生图和视频使用真实媒体接口探测。结果同时写入模型总状态与 `capability_statuses`，因此单项能力失败不会屏蔽同一模型的其他可用能力。媒体测试不会自动运行，设置页会提示可能产生上游费用；远程真实网关的逐项测试需要用户主动点击并验收后再合并。

## 9. 本轮完成定义

本轮“收尾”不代表所有规划功能完成，而是满足以下条件：

1. 当前分支的产物收口补丁完成本地测试并部署；
2. P1-09、P1-12 和 P1-01 的待验收路径有明确操作步骤和结果记录；
3. 新开发顺序、难度、前后端范围、数据边界和分支策略已经记录；
4. 用户确认收尾结果后，才从 `develop` 创建 `feature/history-process-restore` 开始下一批。
