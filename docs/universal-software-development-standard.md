# 通用软件项目开发规范与流程

> 版本：v1.0
> 适用范围：个人项目、团队项目、后端、前端、客户端、CLI、服务、库和数据处理项目。
> 使用方式：本文是与语言、框架和产品类型无关的基础规范。具体项目可以在本文之上增加技术栈、目录、命令和发布要求，但不应降低安全、测试、审查和可追溯性要求。

## 1. 目的

这份文档用于统一软件项目从需求到交付的工作方式，解决以下常见问题：

- 需求没有完成定义，开发结束后仍无法判断是否完成；
- 业务规则、界面、数据库和外部服务混在同一个模块中；
- 代码可以运行，但没有测试、审查和回滚方案；
- 错误、超时、重试、取消、权限和数据恢复没有设计；
- 文档、示例、接口和实际代码逐渐不一致；
- 项目依赖个人经验，换人后难以维护和扩展。

本规范强调四个结果：

1. 代码结构清晰，职责可以定位；
2. 行为有契约，变更可以验证；
3. 风险有门禁，问题可以发现和恢复；
4. 过程有记录，结果可以复核和交接。

## 2. 采用方式

每个项目建立自己的 `PROJECT-DEVELOPMENT.md` 或类似入口文档，至少说明：

- 项目目标和非目标；
- 使用的语言、框架、运行环境和目录约定；
- 本项目的测试、检查、构建和发布命令；
- 哪些规则是强制门禁，哪些只是推荐实践；
- 负责人、审查人和发布责任；
- 本规范中哪些章节被采用、裁剪或扩展。

本文是通用基线，不代替项目的 API 契约、安全策略、运维手册或法律合规要求。

## 3. 基本原则

### 3.1 先定义结果，再开始实现

每项工作都必须先明确用户、问题、范围、非目标和完成标准。没有完成定义的任务只能处于分析状态，不能直接标记为完成。

### 3.2 一个模块只有一个主要变化原因

业务规则、外部协议、数据访问、展示格式和运行控制应分开。模块可以协作，但不能把所有变化原因堆在一个文件或一个类中。

### 3.3 依赖抽象，隔离外部世界

数据库、网络、文件系统、消息队列、模型服务、操作系统和 UI 都属于可变化的外部边界。核心规则通过接口、端口或明确的适配器与它们连接。

### 3.4 默认安全，显式授权

输入不可信，权限不能推断，敏感数据不能默认记录。高风险动作必须经过明确策略、审批或受控执行器。

### 3.5 小步修改，持续验证

一次变更尽量只解决一个问题。先运行最小相关检查，再运行项目完整门禁；不要把无关格式化、重命名和功能开发混在一起。

### 3.6 事实、状态和展示分离

持久化事实、当前状态、缓存投影和用户界面不是同一个概念。修改事实时要考虑重放、恢复、幂等和迁移；展示层不能偷偷改变业务状态。

### 3.7 可读性优先于技巧

优先使用直白的数据流、明确命名和小函数。复杂算法、并发、缓存和抽象只有在解决实际问题时才引入，并写明原因和边界。

## 4. 项目分层与依赖方向

可以使用以下通用分层模型：

```text
接口层       Web / App / CLI / RPC / 消息消费者
    ↓
应用层       用例、事务编排、权限入口、工作流
    ↓
领域层       业务规则、实体、值对象、状态和契约
    ↓
基础设施层   数据库、网络、文件、队列、第三方服务、系统调用
```

约束：

- 接口层负责解析输入、调用用例和格式化输出，不实现核心业务规则；
- 应用层负责流程编排、事务边界、重试策略和依赖注入，不直接散落 SQL/HTTP 细节；
- 领域层应尽量独立、可测试，不依赖具体框架和部署环境；
- 基础设施层实现外部系统适配，并将外部异常转换成项目自己的错误契约；
- 低层不能反向调用高层；跨层共享结构必须进入明确的模型或契约模块。

小型项目可以暂时合并目录，但必须保留上述职责边界；项目变大后按变化原因拆分，而不是按文件数量机械拆分。

## 5. 推荐设计模式

设计模式不是强制清单。使用前必须回答“它隔离了什么变化”以及“它如何提高测试性”。

| 模式 | 解决的问题 | 常见使用场景 |
| --- | --- | --- |
| Ports and Adapters | 核心逻辑被外部服务绑死 | 数据库、支付、模型、消息、文件、系统调用 |
| Service/Use Case | 多步骤业务流程散落在接口层 | 创建订单、审批、导入、编排任务 |
| Repository | 持久化细节污染业务规则 | 聚合读取、保存、查询投影 |
| Strategy | 同一行为有多个可替换算法 | 路由、定价、调度、排序、重试 |
| Factory/Registry | 对象创建和扩展点集中管理 | 插件、Provider、工具、解析器 |
| State Machine | 状态迁移容易被任意修改 | 订单、任务、审批、连接、发布 |
| Adapter | 第三方协议与内部契约不一致 | SDK、HTTP API、旧系统、平台 API |
| Facade | 保持公共入口稳定并隐藏内部拆分 | 兼容旧 API、模块迁移、简化客户端 |
| Observer/Reducer | 多个消费者需要消费同一事件 | UI 状态、日志、审计、实时订阅 |
| Command/Query Separation | 查询产生隐藏副作用 | 管理后台、CLI、审计和维护工具 |

避免以下反模式：无边界的 `utils` 模块、万能 Service、巨型 Controller、全局可变状态、隐式单例、复制粘贴的权限判断和用异常字符串驱动业务分支。

## 6. 文件与代码规范

### 6.1 命名

- 文件、函数和变量使用所在语言的主流规范，并保持同一项目内一致；
- 名称表达职责，不使用含义模糊的 `common`、`misc`、`tmp`、`manager` 作为最终边界；
- 对外接口、事件、错误码和配置项使用稳定名称，变更需要迁移说明；
- 布尔值使用能表达判断含义的名称，例如 `is_active`、`can_retry`；
- ID、时间、金额、单位必须在名称或类型中表达清楚；
- 公共接口的参数和返回值应有类型或 schema 约束。

### 6.2 文件和函数大小

建议阈值如下，具体项目可以调整，但必须记录理由：

- 单文件建议不超过 400 行，超过 600 行需要拆分计划或技术债记录；
- 单函数建议不超过 60 行，超过 100 行优先拆成校验、转换、执行和持久化步骤；
- 一个类只承担一个主要变化原因；
- 测试按功能域拆分，避免所有测试集中在一个文件；
- 兼容层可以保留历史复杂度，但新功能必须进入清晰的新模块。

### 6.3 注释和文档字符串

注释解释“为什么”，而不是重复“做了什么”。必须说明的内容包括：

- 不明显的业务约束；
- 并发、缓存、重试和一致性取舍；
- 安全边界和不可绕过的检查；
- 兼容逻辑、迁移逻辑和临时限制；
- 外部协议的特殊行为。

## 7. 标准开发流程

### 阶段 A：需求分析

记录以下内容：

```text
背景：为什么要做
用户/调用方：谁会使用
目标：完成后改变什么
非目标：明确不做什么
范围：影响哪些模块和接口
约束：性能、安全、兼容、时间、成本
完成定义：如何证明已经完成
```

如果需求存在多个合理解释，应先记录假设和取舍，不要把关键决策隐藏在代码中。

### 阶段 B：方案设计

设计至少包含：

1. 现状和根因，而不是只描述表面现象；
2. 模块边界、依赖方向和关键数据流；
3. 数据结构、API、事件、状态和错误契约；
4. 权限、敏感数据和审计边界；
5. 超时、重试、取消、幂等、恢复和迁移方案；
6. 测试层级和真实验收方式；
7. 备选方案、取舍和已知限制。

小改动可以把设计写在任务或 PR 描述中；跨模块、协议、数据和安全变更必须形成独立设计文档。

### 阶段 C：实现

推荐实现顺序：

1. 契约、模型和错误类型；
2. 领域规则；
3. 应用用例；
4. 基础设施适配器；
5. 接口和展示层；
6. 迁移、文档、示例和兼容处理。

保持每一步可运行、可测试。遇到遗留大文件时，用兼容门面逐步迁移，不要为了“彻底重写”而扩大无关范围。

### 阶段 D：验证

验证顺序应从快到慢、从局部到全局：

```text
格式/类型/语法
    → 单元测试
    → 契约和集成测试
    → 端到端/接口测试
    → 安全和性能检查
    → 构建与发布检查
    → 真实环境 smoke
```

每项检查必须有明确结果。仅仅“没有报错”不等于覆盖了需求，必须确认测试确实验证了相关行为。

### 阶段 E：代码审查

审查重点按以下顺序：

1. 需求和完成定义是否满足；
2. 设计是否解决根因，是否引入不必要复杂度；
3. 数据、接口、事件和兼容行为是否稳定；
4. 权限、输入校验、敏感数据和审计是否完整；
5. 失败、超时、取消、重试、恢复和幂等是否正确；
6. 模块边界、依赖方向、命名和可读性是否合理；
7. 测试是否覆盖新增风险和回归路径；
8. 文档、帮助、迁移和发布说明是否同步。

审查意见分为：

- **阻塞项**：合并前必须修复；
- **非阻塞建议**：本次可合并，但需要记录后续任务；
- **确认项**：需要作者补充证据或说明。

通过测试不能替代代码审查；通过代码审查也不能替代必要的真实环境验收。

### 阶段 F：发布与复盘

发布前确认版本、迁移、配置、回滚和监控方案。发布后记录：

- 实际变更与计划的差异；
- 失败和回滚情况；
- 用户反馈和指标变化；
- 遗留风险和后续行动。

## 8. 测试标准

### 8.1 测试层级

| 层级 | 目标 | 特征 |
| --- | --- | --- |
| 单元测试 | 验证纯规则和小模块 | 快、确定、边界多 |
| 契约测试 | 验证 API、事件、schema | 保护调用方和兼容性 |
| 集成测试 | 验证模块组合 | 使用受控数据库、文件或 fake 外部服务 |
| 端到端测试 | 验证真实用户流程 | 覆盖关键主链路和关键失败路径 |
| Smoke 测试 | 验证环境可用 | 短、稳定、适合发布前执行 |
| 性能/容量测试 | 验证资源和延迟 | 有基线、阈值和可重复数据 |
| 安全测试 | 验证边界不可绕过 | 输入、权限、密钥、审计、依赖 |

### 8.2 必测异常路径

按功能适用范围覆盖：

- 空输入、非法输入、超大输入；
- 网络失败、依赖不可用、响应格式错误；
- 超时、限流、重试和重复提交；
- 并发、取消、进程退出和恢复；
- 权限拒绝、审批拒绝、越界资源；
- 数据库迁移失败、部分写入和投影重建；
- 版本不兼容和旧客户端调用。

### 8.3 测试质量

- 测试名称描述行为和条件；
- 避免只验证实现细节；
- 测试失败时能快速定位；
- 测试数据不包含真实凭据或个人信息；
- 不使用不稳定的真实网络作为唯一门禁；
- 真实网络、真实服务和真实发布环境通过单独 smoke 或验收执行。

## 9. 质量门禁

每个项目至少建立以下门禁，并在 CI 和本地提供统一入口：

1. 语法、格式、类型或编译检查；
2. 单元、契约和集成测试；
3. 安全扫描、敏感信息扫描和依赖漏洞检查；
4. 架构/目录/命名/生成文件一致性检查；
5. 构建、打包和最小启动 smoke；
6. 数据库迁移、回滚和配置校验（如适用）；
7. `diff`、许可证、文档链接和变更说明检查。

质量门禁应：

- 使用一条清晰命令运行；
- 输出必要的 PASS/FAIL 和失败原因；
- 失败时返回非零退出码；
- 使用隔离临时数据，不修改开发者真实数据；
- 不要求把真实密钥写入命令行或仓库；
- 避免把不可控外部服务作为每次提交的必需条件。

示例：

```text
project check
project test
project build
project verify
```

具体命令由项目定义，但提交说明必须写清实际运行的命令和结果。

## 10. 安全与数据保护

### 10.1 输入和权限

- 所有外部输入都经过格式、长度、范围和业务校验；
- 不以客户端隐藏字段、前端按钮或调用方自报身份作为唯一权限依据；
- 权限在服务端/核心用例边界再次校验；
- 高风险动作默认拒绝或要求显式授权；
- 路径、命令、SQL、模板、URL 和序列化输入使用安全 API，避免字符串拼接。

### 10.2 密钥和敏感数据

- 使用环境变量、密钥管理服务或操作系统凭据存储；
- 日志、错误、监控、截图、测试夹具和文档不得包含真实凭据；
- 脱敏策略必须测试，不能只依赖人工检查；
- 发现泄露时立即停止传播、清理来源、轮换凭据并记录事件。

### 10.3 审计与隐私

审计记录“谁在什么时候对什么资源做了什么决定以及结果如何”，但不应复制完整敏感内容。明确数据保留期限、访问范围、删除方式和导出边界。

## 11. 接口、错误和事件规范

### 11.1 接口

对外接口必须有：

- 版本策略；
- 请求和响应 schema；
- 必填/可选字段和默认值；
- 错误码、可重试性和恢复建议；
- 超时、分页、幂等和并发说明；
- 兼容和废弃策略。

### 11.2 错误

错误至少包含稳定的机器可读 code 和用户可理解的 message；适用时增加 `retryable`、`request_id`、`resource_id`、`recovery` 和安全的 details。

不要把堆栈、密钥、SQL、内部路径或第三方原始响应直接返回给用户。内部日志可以保留受控诊断，但同样必须脱敏。

### 11.3 事件

事件应包含稳定类型、唯一 ID、顺序信息、时间、作用域和最小 payload。事件消费者必须能处理重复、乱序、延迟、断线和未知事件；新增字段应向后兼容。

## 12. 数据迁移、恢复和可运维性

涉及持久化的变更必须回答：

- 旧数据如何读取；
- 新数据如何写入；
- 迁移是否可重复、可观测和可回滚；
- 部分失败时如何恢复；
- 是否需要备份和 dry-run；
- 投影、缓存和索引如何重建；
- 用户如何知道迁移状态。

长任务、后台任务和定时任务需要明确 owner、租约/心跳、取消、重试、超时、孤儿任务处理和恢复方式。

## 13. 文档与知识维护

文档至少分为：

- README：项目定位、快速开始和最短可用路径；
- 开发手册：目录、命令、测试、门禁和本地环境；
- 架构/设计文档：模块、数据流、边界和取舍；
- API/协议文档：schema、错误、版本和示例；
- 运维/发布文档：配置、迁移、监控、回滚和恢复；
- 验收记录：实际运行的命令、结果、证据和限制。

功能、命令、配置、接口、状态或设计变化时，必须同步更新适用文档。文档中的命令应定期在干净环境执行，避免只维护“看起来正确”的示例。

## 14. 变更检查清单

### 新功能

- [ ] 需求、范围、非目标和完成定义明确
- [ ] 模块边界、依赖方向和设计取舍明确
- [ ] 输入、输出、状态、错误和权限契约明确
- [ ] 正常和异常路径有测试
- [ ] 文档、示例和迁移说明已更新
- [ ] 聚焦检查和完整门禁通过
- [ ] 真实 smoke 已执行或说明不适用

### Bug 修复

- [ ] 有最小复现
- [ ] 已确认根因
- [ ] 先增加失败回归测试
- [ ] 检查同类路径和边界条件
- [ ] 验证不会破坏兼容、安全和恢复行为
- [ ] 记录用户可观察的修复结果

### 重构

- [ ] 已盘点公共 API、数据、事件和调用方
- [ ] 新旧入口有兼容或迁移策略
- [ ] 新模块职责更清晰，文件和函数规模可控
- [ ] 无无关行为变化
- [ ] 测试、门禁和文档均通过
- [ ] 已记录废弃和删除计划

### 发布

- [ ] 版本、配置和迁移准备完成
- [ ] 构建产物可复现或有来源记录
- [ ] 备份、回滚和恢复方案已验证
- [ ] 监控、日志和告警已准备
- [ ] 发布说明包含已知限制
- [ ] 发布后有复盘和后续任务

## 15. Definition of Done

一个变更只有在以下条件全部满足时才可以标记为完成：

1. 需求范围和完成定义已经明确；
2. 实现位于正确的模块边界，命名和依赖符合项目规范；
3. 对外行为、数据、接口、事件或配置契约已经更新并可验证；
4. 正常路径和适用的失败、超时、取消、重试、恢复、幂等路径已有测试；
5. 安全、权限、隐私、审计和敏感数据边界没有被绕过；
6. 必要的用户界面、日志、诊断和恢复提示已经可用；
7. 文档、示例、迁移、发布和回滚说明已经同步；
8. 项目质量门禁通过；
9. 代码审查没有阻塞项；
10. 交付记录包含可复核的命令、结果和已知限制。

## 16. 通用交付记录模板

```text
标题：<变更名称>

背景：<为什么需要这项变更>
目标：<完成后用户/系统得到什么>
范围：<涉及的模块、接口、数据和文档>
非目标：<明确不包含的内容>

设计：
- <边界和关键取舍>
- <状态、错误、权限和恢复处理>

实现：
- <关键文件/模块>
- <兼容、迁移或废弃处理>

验证：
- <聚焦测试命令>：通过/失败
- <完整门禁命令>：通过/失败
- <真实 smoke 或人工验收>：通过/未执行/不适用

审查：
- 阻塞项：<无/列表>
- 非阻塞建议：<无/列表>

已知限制：
- <限制、风险和影响>

后续：
- <必须继续的工作>
```

## 17. 项目落地时的最小目录

不同语言可以使用不同名称，但建议至少有以下知识入口：

```text
README.md                         # 用户快速开始
CONTRIBUTING.md                   # 贡献和提交规则
docs/development-guide.md         # 项目开发手册，引用本文并补充项目细节
docs/architecture.md              # 架构和模块边界
docs/quality-gate.md              # 门禁和验证命令
docs/decisions/                   # 重要设计决策（ADR）
docs/acceptance/                  # 可复核验收记录
scripts/                          # check/test/build/smoke 入口
tests/                            # 按功能和层级组织的测试
```

采用本文后，项目应把技术栈细节写入自己的开发手册，把可复用的流程、门禁、审查和完成定义保留在本规范中。这样既能保持统一工程质量，也不会把某个项目的实现方式误当成所有项目的唯一答案。
