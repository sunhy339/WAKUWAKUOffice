# 模型能力配置与自动路由设计

> 状态：开发中（视频候选模型回退已实现，设置页路由预览待开发）
> 
> 适用分支：`feature/model-route-finalization`
> 
> 目标：在不破坏现有对话、图片和视频功能的前提下，让 WaKuOffice 按任务能力选择对应模型和协议。

## 1. 背景与现状

当前项目已经在环境变量层面区分了文本、图片和视频配置：

- `LLM_TEXT_*`：对话、工具调用和方案规划；
- `LLM_IMAGE_*`：图片生成；
- `LLM_VIDEO_*`：视频生成。

但是用户设置页的模型仍然只是 `models: string[]`，没有能力信息。执行侧也存在两套行为：

- `LlmClient` 根据用户当前配置执行文本对话；
- `image_prompt` 和 `video_generate` 直接读取服务端的图片/视频环境变量。

因此，当前“模型列表”不能回答“这个模型支持什么”，用户在设置页选择的对话模型也不会自动改变生图模型。模型名称前缀过滤只能避免明显的误用，不能处理自定义模型名、同一网关暴露多种能力、协议不同或能力不完整的情况。

线上实际探测还发现，当前网关的 `/v1/models` 返回的模型名不能直接当作能力清单：同一个网关可能在文本、图片和视频入口返回相同列表，而接口是否真正支持某种能力需要配置标注或能力测试确认。

## 2. 目标与非目标

### 目标

1. 管理员可以在一个模型服务下配置多个模型，并为每个模型标注能力。
2. 对话、识图、文生图、图生图、视频生成分别使用满足能力要求的模型。
3. 保留现有环境变量和用户设置格式，旧配置可以继续运行。
4. 对能力不确定、接口不支持、超时、限流和上游 5xx 给出可恢复的状态和可读错误。
5. 允许管理员按能力设置默认模型、备用模型和优先级。

### 非目标

- 第一阶段不做所有供应商的专有协议适配；先支持现有 OpenAI 兼容网关。
- 第一阶段不自动推断模型“质量”或成本，只判断/记录接口能力和可用性。
- 第一阶段不让普通用户修改服务端全局 Key；继续沿用当前的用户配置和服务端环境变量边界。

## 3. 能力模型

模型能力与模型名称解耦，建议第一阶段使用以下枚举：

| 能力 | 含义 | 典型调用 |
|---|---|---|
| `text` | 普通文本生成、结构化输出 | Chat Completions 或 Responses |
| `tool_calling` | 工具调用和 Agent 编排 | Chat Completions/Responses + tools |
| `vision` | 输入图片并理解、OCR、分析截图 | 多模态 Chat/Responses |
| `image_generation` | 文生图 | `/v1/images/generations` 或适配器 |
| `image_edit` | 图生图、参考图编辑 | 图片生成接口的 image 输入 |
| `video_generation` | 文生视频或图生视频 | 视频生成适配器 |

`text`、`tool_calling`、`vision` 是对话模型的输入/输出能力；`image_generation`、`image_edit`、`video_generation` 是媒体生成能力。一个模型可以有多个能力，但路由时必须满足任务的全部硬性要求。

## 4. 数据结构与兼容迁移

在现有 `LlmProfileConfig` 上增加可选字段，不删除原来的 `models`：

```text
LlmProfileConfig
  id, name, base_url, provider, wire_api, reasoning_effort
  api_keys, models, default_model
  model_configs: LlmModelConfig[]   // 新字段，serde default

LlmModelConfig
  model: string
  capabilities: ModelCapability[]
  enabled: bool
  priority: integer
  status: unknown | available | unavailable
  last_checked_at: timestamp?
  last_error: string?
```

迁移规则：

1. 读取旧配置时，如果 `model_configs` 为空，则根据 `models` 生成模型配置。
2. 旧模型默认标注 `text`；如果模型名符合 `gpt-image-*`、`image-*` 等现有媒体规则，则默认标注对应媒体能力，但状态为 `unknown`。
3. 现有 `default_model` 继续作为对话默认模型。
4. 新增按能力的默认模型映射，例如 `default_models: { text, vision, image_generation, ... }`；缺失时回退到旧的环境变量默认值。
5. 保存时同时维护旧 `models` 投影，确保旧前端和已有用户设置仍可读取。

Key 仍只保存服务端必要的密钥字段，并沿用现有掩码和 Key 池规则；能力配置不包含 API Key。

## 5. 路由设计

新增应用层 `ModelRouter`，不让每个工具自己拼模型选择规则：

```text
用户请求
  → Intent/工具确定任务类型
  → 生成 ModelRequirement
  → ModelRouter 按能力、启用状态、优先级筛选
  → Provider Adapter 按 wire_api 执行
  → 统一结果/错误/事件
```

任务与能力映射：

| 任务 | 必需能力 | 路由说明 |
|---|---|---|
| 普通对话 | `text` | 优先用户选中的对话模型 |
| 工具型办公任务 | `text` + `tool_calling` | 不选择仅支持文本输出的模型 |
| 识图/OCR/截图分析 | `vision` | 使用支持图片输入的模型 |
| 文生图 | `text`（规划）+ `image_generation`（执行） | 规划模型和生图模型独立选择 |
| 图生图 | `vision`（理解参考图，可选）+ `image_edit` | 生图请求必须携带参考图 |
| 视频方案 | `text` | 方案生成失败可使用规则兜底 |
| 视频生成 | `video_generation` | 不复用普通对话模型 |

关键原则：用户在顶部选择的模型只代表当前对话/规划模型；媒体生成模型按任务能力单独路由。高级用户可以在设置中覆盖，但不能让普通文本选择绕过能力校验。

## 6. Provider Adapter

对外保留现有工具入口，对内拆出适配器：

- `TextModelAdapter`：统一 Chat Completions、Responses 的输入、工具、结构化输出和重试。
- `VisionModelAdapter`：复用文本协议，但校验图片输入并优先选择 `vision` 能力。
- `ImageModelAdapter`：统一模型、尺寸、比例、参考图、URL/base64 响应；先兼容现有 `/v1/images/generations`。
- `VideoModelAdapter`：保留当前视频请求格式，后续再隔离供应商差异。

`image_prompt` 只负责方案编排和产物生成，不再直接决定 `LLM_IMAGE_MODEL`；当用户模型配置没有可用的 `image_generation` 时，兼容回退到服务端 `LLM_IMAGE_*` 配置。这样可以先接入路由，再逐步迁移现有工具。

## 7. 能力识别策略

能力识别分三级，避免把不可靠的 `/models` 结果当成事实：

1. **显式配置（最高优先级）**：管理员在模型行勾选能力。
2. **受控探测**：点击“测试能力”后，对文本、视觉、图片、视频分别发最小请求；成功才标记 `available`，失败记录错误但不删除配置。
3. **名称启发式（最低优先级）**：只作为初始建议，例如 `image`、`video`、`vision`；必须显示“待确认”，不能直接作为可用事实。

探测必须可取消、有限时、脱敏记录，不把完整 Key、图片数据或模型响应全文写入日志。

## 8. 前端设计

沿用当前设置弹窗、暖灰背景、半透明卡片、黑色主按钮和 Lucide 图标，不新增独立管理后台页面。模型服务卡片改为：

1. 服务基础信息：名称、Provider、Base URL、Wire API、Key 池。
2. 模型列表：模型名、能力标签、启用开关、优先级、状态。
3. 操作：获取模型、测试连接、测试能力、设为某能力默认模型。
4. 路由预览：显示“对话 / 识图 / 生图 / 视频”当前将使用哪个模型。

状态必须区分加载、未知、可用、不可用、保存失败和重试；能力标签不能只依赖颜色，需同时显示文字和状态图标。旧配置打开时自动展示为“文本能力 + 待确认媒体能力”，不改变现有选择。

## 9. 错误、重试和回退

- 401/403/429/5xx：按当前 Key 池轮询，并遵守有限重试次数。
- 502/503/504：短退避后重试；同一任务不无限重试。
- 没有匹配能力：在执行前返回“未配置可用的 X 模型”，同时给出设置入口，不把请求发给错误模型。
- 图片规划失败：优先切换文本备用模型；规划仍失败时明确区分“文本规划失败”和“图片接口失败”。
- 图片接口成功但没有 URL/base64：记录协议不匹配，提示检查 Provider Adapter，而不是泛化成“生成失败”。
- 任务取消：取消规划和媒体请求，不能在取消后继续写入产物。

## 10. 开发拆分与难度

| 子任务 | 范围 | 难度 | 预计工作量 | 验收重点 |
|---|---|---:|---:|---|
| R1 能力模型兼容迁移 | Rust/TypeScript 类型、旧设置迁移、按能力默认值 | 中 | 1～2 天 | 旧配置读取/保存不丢失，旧对话不变 |
| R2 ModelRouter | 需求模型、筛选、优先级、备用模型、错误契约 | 中高 | 2～3 天 | 文本/视觉/图片/视频不会串用 |
| R3 Provider Adapter | 图片接口先接入，保留现有图片/视频回退 | 中高 | 2～4 天 | URL/base64、图生图、超时和重试 |
| R4 设置页能力管理 | 模型行、能力标签、测试能力、默认路由预览 | 中 | 2～3 天 | 现有风格、响应式、状态完整 |
| R5 真实服务验收 | 使用远程网关逐项探测，覆盖失败与回退 | 中 | 1～2 天 | 记录请求类型、模型、结果和清理方式 |

建议先做 R1 + R2，再做 R3；R4 可以与 R3 并行，但在路由契约稳定前不应先改 UI 逻辑。整体预计 8～14 个工作日，取决于网关对 Responses、多模态、图片和视频协议的实际兼容程度。

## 11. 完成定义

本功能只有同时满足以下条件才可标记为“已完成”：

1. 旧的单模型设置、环境变量配置和普通对话通过回归测试。
2. 用户可以为同一服务的不同模型标注能力并保存。
3. 普通对话、识图、文生图、图生图、视频生成各自命中正确能力模型。
4. 没有匹配模型时前端可读地提示配置，不产生错误产物。
5. 至少覆盖 401、429、502、超时、取消和图片响应缺字段。
6. 远程真实网关完成文本、生图和至少一种多模态路径验收；Key、图片内容和敏感响应不进入仓库或普通日志。
